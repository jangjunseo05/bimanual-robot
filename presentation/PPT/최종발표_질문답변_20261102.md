## 1. 7쪽: 그리퍼 과부하 예방은 어떤 로직인가?

**결론: 서보의 목표 위치를 실제 위치 바로 옆(10틱)으로 당겨서 미는 힘을 줄이는 로직이다. 정책이 끝난 뒤와 다음 실행 전에 돌고, 정책이 움직이는 동안에는 돌지 않는다.**

쉬운 설명: 위치 제어 서보는 "목표 위치와 실제 위치의 차이"만큼 힘을 낸다. 컵을 쥐면 손가락은 컵에 막혀 못 가는데 목표는 컵 안쪽에 있어서, 서보가 계속 밀며 뜨거워지고 과부하 보호가 걸린다. 그래서 목표를 실제 위치 가까이 옮겨 "목표-실제" 차이를 줄인다. 토크는 켠 채이므로 손가락은 그대로 있고 컵도 놓치지 않는다.

왜 필요했나: 물따르기 뒤 컵을 쥔 채 기다리다 왼손 그리퍼(ID 6)에 과부하 보호가 걸렸고, 다음 연결이 `Missing motor ID 6`으로 실패했다(PROGRESS 2026-10-22).

함수 `relax_gripper` (`tools/rollout/rollout_handoff.py:188-221`)의 동작:

1. 그리퍼(ID 6)의 토크 상태를 읽는다. 응답이 없거나 토크가 꺼져 있으면 아무것도 하지 않는다.
2. 목표(`goal`)와 실제 위치(`pres`)를 읽고 `diff = goal - pres`를 계산한다.
3. `abs(diff) > margin`이면 목표를 `pres ± margin`으로 바꾼다(부호는 `diff`와 같은 쪽). `margin` 기본값은 **10틱**이고 약 0.9°다(`rollout_service.py:175`).
   - 예시값: goal 2000, present 1900이면 차이 100 → 새 goal 1910.
4. `clear_overload=True`일 때 서보 오류값의 과부하 비트(`OVERLOAD_BIT = 32`)가 켜져 있으면 1초 기다렸다 다시 읽는다. 그래도 켜져 있으면 토크를 껐다 바로 켜서 보호 상태를 푼다(줄 211-221).

언제 돌아가나:

| 시점 | 호출 | 과부하 해제까지 하나 |
|---|---|---|
| 실행기 시작 전, 팔 연결 전 | `pre_relax` → 양팔 (`rollout_handoff.py:224`, `rollout_service.py:708-711`) | 예 |
| 물따르기가 끝나고 그 자세로 유지할 때, 또는 작업이 중단·실패했을 때 | `_finish_pose`의 `relax_grippers` (`rollout_service.py:564-568`) | 아니오 |
| 팔 연결이 끊긴 채 작업이 끝났을 때 | `rollout_service.py:550-553` | 아니오 |
| 실행기 종료 시 | `Service.close` (`rollout_service.py:607-612`) | 아니오 |

컵배치가 정상으로 끝나 끝 자세로 갈 때는 이 로직을 부르지 않는다(`hold`가 거짓). 줄 564의 조건 때문이다.

별도 보호 하나 더: `start_scenario.bat:22`는 **왼팔에만** `gripper_protection=true`를 준다. 연결할 때 서보 자체 한계를 쓰는 설정으로, 이 PC의 lerobot 코드 값은 최대 토크 500, 보호 전류 250, 과부하 토크 25다(`lerobot: robots/so_follower/so_follower.py:168-171`). 오른손 ggao50은 닫는 데만 부하 35%가 들어 이 값이면 정상 동작에서도 걸리므로 끈다(`tools/servo/lerobot_gripper_protection.patch:13`). `tools/recording/gripper_protection_strength_tune.patch`에는 700/300/50으로 올린 패치가 있는데 이 PC 설치본에는 적용돼 있지 않다. 시연 노트북이 어느 값인지는 확인이 필요하다.

## 2. 12쪽: "ROS2 Action 계약" → "주문 서버 API 계약" 수정이 맞는가?

**결론: 수정이 맞다. 실제 시연 구조에서 파트들은 ROS Action이 아니라 HTTP로 주문 서버를 통해 만난다. "둘 다 맞다"가 아니므로 ROS 쪽을 쓰면 사실과 달라진다. 추천 문구는 "주문 서버 HTTP API 계약"이다.**

쉬운 설명: ROS 2 Action은 Pi 안에서 Nav2를 부르는 데 쓴다. 파트 사이의 약속은 웹 주소로 주고받는 HTTP다. 주행 쪽이 "정렬 끝났어"를 주소 하나로 보내고, 조작 쪽 상태도 주소 하나로 읽는다.

실제 연결:

| 구간 | 방식 | 근거 |
|---|---|---|
| 주행 PC → 주문 서버(노트북 :8765) | `POST /api/align/confirm`, `GET /api/state` | `tools/jdamr/water_service.py:195, 603`, `docs/guides/20261029_주행_조작_연동_구현명세.md` 4절 |
| 주문 서버 → 조작 실행기(같은 노트북 :8770) | `POST /run/pour`, `/run/place`, `/stow`, `/stop` | `tools/rollout/rollout_service.py:24-29` |
| Pi 내부 | ROS 2 Jazzy·Nav2 | 구현명세 45줄: LOCALHOST 탐색이라 외부에서 ROS로 직접 붙을 수 없다 |

ROS 2 Action 계약(`ExecuteManipulationSkill`, #47)은 실제로 만들었지만 **시뮬레이션 전용 mock**이고 `dry_run=false`를 거부한다(`docs/experiments/20260922_ExecuteManipulationSkill_ROS2_Action.md` 1절). 시연 실행은 `--backend rollout-service`다(`start_scenario.bat:26`).

Q&A 대비 한 줄: "출정식의 ROS 2 Action 계약은 시뮬레이션용 mock까지 만들었고, 실물은 Windows 노트북과 Pi를 HTTP 주문 서버로 연결했습니다." 왜 바꿨는지를 적은 결정 기록은 찾지 못했다. Windows 조작 환경과 ROS 망 분리가 이유로 보이지만 **[추측]** 이다.

## 3. 13쪽: 스키드스티어가 뭔가?

**결론: 바퀴 방향을 꺾지 않고, 좌우 바퀴 속도 차이로 차체를 돌리는 구동 방식이다. 탱크나 굴착기(스키드 로더)가 도는 방식과 같다.**

- 왼쪽과 오른쪽 바퀴를 다른 속도로 돌리면 곡선으로 가고, 반대로 돌리면 제자리에서 돈다.
- 회전할 때 바퀴가 바닥에서 옆으로 미끄러진다. 이름의 skid(미끄러짐)가 여기서 왔다.
- 장점은 구조가 단순하고 제자리 회전이 된다는 점이다.
- 단점은 옆으로 곧장 이동(횡이동)을 못 하고, 미끄러짐 때문에 바퀴 회전으로 계산한 위치(odom)가 틀어질 수 있다는 점이다. 16쪽의 "횡이동이 안 돼 근거리 좌우 보정이 어려움"이 이 특성이다.

근거: `design/mechanical/hold_flow_mechanical_v0_3.yaml` 생성 요약의 `skid_steer_four_wheel_drive`(README 단일 원본 요약), 16쪽 재접근 사례(PROGRESS 11-01). 원리 설명은 **[일반 이론]** 이다.

## 4. 13쪽: "설계·URDF 기준" vs "설계 URDF 기준"

**결론: "프레임 치수는 설계·URDF 기준"이 맞다.**

설계 원본(`design/mechanical/hold_flow_mechanical_v0_3.yaml`)과 URDF(`src/description/hold_flow_description/`)는 별개의 파일이고 둘 다 450×340 mm다. 가운뎃점이 없으면 "설계용 URDF" 하나로 읽힌다. 카메라 높이(상판 위 540 mm)와 상판 높이(720 mm)는 YAML에 사용자 확인값으로 기록돼 있어(`provenance`, 줄 19-30) 슬라이드의 구분과도 맞다.

## 5. 17쪽: 이미지 증강 종류

**결론: 6종 가운데 프레임·카메라마다 무작위로 3종을 골라 건다. 밝기, 대비, 채도, 색조, 선명도, 회전·이동이다.**

| 종류 | 값 | 뜻 |
|---|---|---|
| 밝기 brightness | 0.8~1.2배 | 조명 변화 |
| 대비 contrast | 0.8~1.2배 | 명암 차이 변화 |
| 채도 saturation | 0.5~1.5배 | 색 진하기 변화 |
| 색조 hue | -0.05~+0.05 | 색이 살짝 틀어짐 |
| 선명도 sharpness | 0.5~1.5배 | 흐릿함·또렷함 변화 |
| 회전·이동 affine | 회전 ±5°, 이동 가로·세로 ±5% | 카메라가 살짝 틀어진 효과 |

- 6종의 가중치는 모두 1.0이고, 적용 순서는 고정이다.
- 데이터가 늘어나지 않는다. 학습 때 꺼낸 이미지에만 임시로 걸고, 관절값·정답 행동은 그대로다. 검증 6개에는 걸지 않는다.
- 좌우 뒤집기는 없다. 왼팔·오른팔이 구분되는 과제라 맞는 선택이다.
- 왜 넣었나: 브리지 재연결마다 노출이 달랐고, top 카메라가 약 17 px 어긋났으며, 왼쪽 손목캠 기종이 바뀌었기 때문이다.
- **증강 유무를 직접 비교한 결과는 없다.** 효과를 수치로 말하지 않는다.

문서 정정: 실험 기록과 스크립트 주석에는 "최대 3개"라고 적혀 있지만 코드는 항상 정확히 3개를 고른다(`lerobot: transforms/transforms.py:79, 716`). 값 이름만 `max_num_transforms`다. 발표에서는 "3종"으로 말하면 된다.

근거: `체크포인트: water_pour_chassis_smolvla_80/checkpoints/016000/pretrained_model/train_config.json`, `lerobot: datasets/dataset_reader.py:341`, `docs/experiments/20261025_차체결합_SmolVLA_60vs80_학습결과.md` 1절, 2절. 컵배치 80도 증강이 켜져 있음을 같은 파일로 확인했다.

## 6. 20쪽: 래퍼 6개 구체 설명

**결론: 정책은 동작만 만들고, 언제 시작·종료하고 끊김에 어떻게 대응할지는 아래 규칙이 정한다. 값은 모두 현재 시연 실행기 기준이다.**

### 01 시작 자세 (물따르기만)
- 정책 전에 팔을 저장 자세 `config/rollout_poses/pour.json`으로 옮긴다. 시연 데이터의 출발 범위 안에서 시작해 제자리 떨림(OOD)을 막으려는 것이다.
- 이동 시간은 `max(5 s, 가장 큰 관절 차이 / 20°/s)`이고, 처음과 끝이 느린 곡선(smoothstep)으로 움직인다.
- 도착 0.5초 뒤 한 관절이라도 **10°를 넘게** 벗어나 있으면 그 자리를 목표로 고정하고 추론하지 않는다. 결과는 `start_pose_failed`다.
- 그리퍼는 건드리지 않는다. 컵배치는 컵을 쥔 채 시작하므로 시작 자세가 없다.
- 근거: `rollout_handoff.py:291-329`, `rollout_service.py:460-464, 85-86`

### 02 작업 끝 감지 (`DoneDetector`, 약 30 Hz로 매 틱 검사)
- **물따르기:** 오른손 값이 20을 넘었다가(병 쥠) 10 미만으로 내려가면 "병 놓음"으로 본다. 그 뒤 왼팔 5관절이 상판 적재 자세 ±10° 안에 **1초** 머물면 끝이다.
- **컵배치:** 3단계를 순서대로 통과해야 한다.
  1. 왼손 측정값과 명령이 모두 40 초과로 0.3초 유지(컵 놓음)
  2. 놓은 자리에서 왼팔이 10° 이상 빠짐
  3. 왼손이 10 미만으로 닫히고(명령도 10 미만) 왼팔 5관절이 물따르기 시작 자세 ±20° 안에 1초 머묾
- 끝나면 남은 시간을 기다리지 않고 바로 다음 단계로 간다. 최대 시간은 물따르기 100 s, 컵배치 50 s이고, 이때는 성공으로 치지 않는다(`duration`).
- **주의:** 물따르기의 "병 놓음" 조건은 사실상 걸러 주지 못한다. 시작 때 열린 오른손을 정책이 닫으면서 약 1초 만에 켜진다(PROGRESS 11-01). 지금 끝 판정을 실제로 가르는 것은 왼팔 적재 자세 1초다.
- 근거: `rollout_handoff.py:103-167`, `rollout_service.py:84-87`

### 03 과부하 예방
- 1번 답변 내용이다. 그리퍼 목표를 실제 위치 ±10틱으로 당겨 미는 힘을 줄인다. 토크는 유지한다. 정책 전후에 돌고 정책 중에는 돌지 않는다.

### 04 끊김 보호 (`camera_fallback.py`)
- 카메라에서 0.5초 넘게 새 프레임이 없으면 원래 lerobot은 오류를 내고 멈춘다. 이 래퍼는 오류 대신 **마지막 정상 프레임**을 돌려준다.
- 뒤에서 별도 스레드가 다시 연결한다. USB 경로로 장치 번호를 다시 찾고, 재연결을 마친 시점부터 **2초** 뒤 재시도한다.
- 끊긴 동안에는 "연결됨"으로 보이게 해서 카메라 하나 때문에 로봇 전체가 끊긴 것으로 판정되지 않게 한다.
- 손목캠뿐 아니라 실행기가 쓰는 OpenCV 카메라 3대 모두에 걸린다.
- 한계: 끊긴 동안 정책은 멈춘 화면을 본다. 오래 끊기면 판단이 틀릴 수 있고, 스스로 멈추지 않으므로 STOP이 필요하다. 근본 해결은 커넥터 고정(테이핑)이다.
- 근거: `tools/rollout/camera_fallback.py:1-14, 22, 74-75, 86-97, 107-114`, `docs/guides/20261031_주말_통합_전체지도.md` P2

### 05 오른팔 접기
- 물따르기가 **작업 끝 감지로 끝났을 때만** 실행한다. 최대 시간 도달이면 병을 쥐고 있을 수 있어 움직이지 않는다.
- 오른팔 관절만 `place_end` 자세로 옮긴다(그리퍼 제외). 왼팔은 컵을 쥔 상판 적재 자세 그대로다. 그 자세가 컵배치 정책의 시작 자세이기 때문이다.
- 시간 규칙과 10° 허용은 시작 자세와 같다. 성공하면 `arms=carrying_cup`이 되어 주행 출발이 풀린다. 실패하면 `hold`로 멈추고 복구용 `/stow_right`를 쓴다.
- 관절값만 모터 버스에서 읽으므로 손목캠이 끊겨도 실행된다.
- 근거: `rollout_service.py:584-598, 570-571, 105-120, 527-545`

### 06 끝 자세 복귀
- 컵배치 뒤 양팔을 저장 자세 `place_end`로 옮긴다. 이 자세가 곧 주행 중 이동 자세다. 이동 시간 규칙은 같다.
- 작업 끝 감지, 최대 시간, 정상 종료일 때만 간다. 중단·오류면 팔을 움직이지 않는다.
- 작업 끝 감지로 끝났고 도착 확인(±10°)까지 통과해야 `arms=stowed`다. 그 밖에는 `hold`라 주행이 출발하지 않는다.
- 도착 전후 읽기에 `get_observation()`을 쓰므로 카메라까지 읽는다. 05번과 달리 "모터 값만"이 아니다. 끊겼을 때도 진행되는 것은 끊김 보호가 마지막 프레임을 주기 때문이다.
- 근거: `rollout_service.py:563-564, 576-580`, `rollout_handoff.py:241-278`

## 7. 21쪽: 붓기 90° 망설임의 원인과 재수집의 이론

**결론 3줄**
1. "자갈 모습에 의존"은 **확인된 사실이지만, 망설임의 확인된 원인이라고 쓰면 과장**이다. 그 실험은 뚜껑을 닫은 조건이었고, 실제 과제 조건 시험은 그 기록에서 하지 않았다.
2. 사용자의 1)번 이해는 **맞다**. 정식 용어는 관측 모호성(perceptual aliasing)이다.
3. 사용자의 2)번은 방향은 맞지만 **용어 두 개가 틀렸다**. "비어 있는 청크"는 없고, SmolVLA는 "자기회귀 모델"이 아니다. 맞는 말은 "정지 구간의 관측 모호성과 정지 고착"이다.

### 7-0. "자갈 의존"이 원인이 맞나?

기록에서 확인되는 것(`docs/experiments/20261021_물따르기_정책_자갈_시각의존_causal_confusion.md`):

| 조건 | 결과 |
|---|---|
| A. 뚜껑 열림 + 자갈 (학습 조건) | **기록 당시 미실시** |
| B. 뚜껑 닫힘 + 자갈 | 90°까지 기울이고 그 부근에서 왕복 |
| C. 뚜껑 열림 + 빈 병 | 붓기를 건너뛰고 병 반납 |

- B·C는 학습 때 보지 못한 조건(OOD)이다. 정책이 자갈 모습을 본다는 증거로는 강하다. 특히 C가 그렇다.
- 그러나 실제 과제 조건 A에서 망설였는지는 그 문서가 미결로 남겼다. 문서 스스로 "결함인지는 배포 조건에 달렸다"고 적었다.
- 재수집은 자갈을 다양화하지 않았다(v2도 같은 자갈). **즉 재수집은 자갈 의존을 없애는 조치가 아니었다.** 슬라이드처럼 "원인: 자갈 의존 → 조치: 재수집"으로 이으면 앞뒤가 맞지 않는다.
- 재수집이 실제로 바꾼 것은 시연 방식이다. 기울임 유지 시간 평균이 v1 13.4 s에서 v2 6.1 s로 줄었고, 붓기 구간은 40/40 에피소드에서 1회였다(PROGRESS 10-22, 데이터 측정값). 사용자 설명이 실제 조치와 맞는다.
- 다만 v1과 v2 사이에 조건을 하나씩 바꿔 원인을 가른 실험은 없다. 시간·조건을 나눈 비교 기록이 없으므로 **"긴 유지가 망설임의 원인"도 유력 가설**이다. 조건 A 재시험도 기록을 찾지 못했다.
- 사실 두 설명은 이어진다. 시연자가 자갈이 다 빠질 때까지 보고 있었기에 유지가 길어졌고, 정책은 그 구간에서 "언제 끝낼지"를 자갈 화면으로만 판단해야 했다.

참고: 40-ep v1 기준 이야기다. 시연 가이드를 쓴 재수집은 테이블 거치 v2이고, 차체 결합 데이터가 같은 가이드를 따랐다는 측정은 찾지 못했다. 최종 모델 근거로 말할 때는 이 구분을 지킨다. 또 18쪽의 40개 모델 "붓기 반복"처럼 데이터가 적으면 같은 증상이 나왔다.

### 7-1. SmolVLA가 실제로 어떻게 생겼나 (이론의 전제)

| 사실 | 값 | 근거 |
|---|---|---|
| 입력 관측 | **현재 1장뿐**(`n_obs_steps=1`), 카메라 3대 + 관절 위치 12개 + 문장 | `체크포인트: config.json` |
| 속도 입력 | **없음.** 관절 "위치"만 들어간다 | 같은 파일 `observation.state` shape 12 |
| 이전 행동 입력 | **없음** | `lerobot: policies/smolvla/modeling_smolvla.py:552-619` |
| 출력 | 한 번에 50스텝 묶음(`chunk_size=50`) | `config.json` |
| 실행 | 50스텝 전부 눈 감고 실행한 뒤 다시 추론(`n_action_steps=50`), 시간 앙상블 없음 | `modeling_smolvla.py:260-269` |
| 시간 길이 | 30 Hz에서 약 1.7초(실측 약 1.8초) | 전체지도 P1 |
| 생성 방식 | 플로우 매칭. 무작위 노이즈에서 10단계로 행동 묶음을 만든다 | `modeling_smolvla.py:701, 723, 742, 757` |

한마디로 **기억도, 시계도, 속도계도 없고, 약 1.7초마다 한 번 보고 다음 1.7초를 통째로 계획하는 모델**이다.

### 7-2. 같은 자세가 반복되지 않게 (사용자 1번): 맞는 이해

정식 용어: **관측 모호성(perceptual aliasing, 상태 앨리어싱)**. 서로 다른 상황이 입력으로는 똑같이 보이는 문제다.

- 병을 올리는 중이든 내리는 중이든 같은 각도를 지나면 관절 위치가 같다. 속도와 이전 행동이 입력에 없으므로 위치만으로는 방향을 알 수 없다.
- 그래서 시연 데이터에 "같은 관측 → 올려라"와 "같은 관측 → 내려라"가 함께 들어간다.
- 플로우 매칭은 여러 답을 가진 분포를 표현할 수 있다. 그러면 **평균을 내서 멈춘다기보다, 청크를 뽑을 때마다 둘 중 하나가 나올 수 있다.** 들었다 내렸다 하거나 두 번 붓는 증상이 여기에 맞는다. 정책이 실제로 그렇게 동작하는지는 추론 분포를 재 본 기록이 없어 **[일반 이론 + 추론]** 이다.
- 청크는 입력 문제를 풀지 못한다. 청크의 효과는 "한 번 정한 뒤 약 1.7초는 밀고 간다"는 것이고, 모호한 자세가 **청크 경계**에 걸리면 다시 갈림길이 된다.
- 재수집 규칙의 이유: 병을 든 채 컵 위에 머물지 않고 곧장 내려놓을 자리로 가게 했다. 머물면 그 장면이 붓기 전 장면과 비슷해지기 때문이다. 또 다시 기울인 판은 버렸다(`docs/guides/20261021_핸드오프_시연_가이드_쉬운설명.md` 1장 5·6번).
- 예시 표현 교정: "물을 다 따르고 내리는 과정을 따르려고 올리는 과정으로 착각한다"는 말은 쉬운 설명으로 충분하다. 단 모델이 "착각"하는 것이 아니라 **두 상황을 구분할 입력이 없는 것**이다.

연결되는 점: 병 안 자갈이 보이느냐는 붓기 전후를 가르는 몇 안 되는 단서다. 기억이 없는 모델이 자갈 화면을 쓰는 것은 일종의 기억 대용이라, 자갈 의존과 관측 모호성은 별개가 아니다. **[추론]**

### 7-3. 끊김 없이 부드럽게 시연 (사용자 2번): 용어 교정

**① "비어 있는 청크"는 없다.** 정책은 항상 50스텝을 꽉 채워 낸다. 실제로 비는 경우는 에피소드 끝에서 뒤쪽 스텝이 모자랄 때뿐이고, 이 부분은 손실 계산에서 빠진다(`action_is_pad`, `modeling_smolvla.py:299-329`). 들은 말의 실제 의미는 아마 **"움직임이 거의 없는 청크(정지 청크)"** 일 것이다.

**② "자기회귀" 표현은 SmolVLA에 맞지 않는다.** 자기회귀 모델은 자기 이전 출력을 다음 입력으로 넣는 모델이다. SmolVLA는 이전 행동을 입력으로 받지 않고, 청크 하나를 한 번에 만든다. 10단계 반복은 노이즈를 행동으로 다듬는 샘플링 과정이지 시간 순서 예측이 아니다.

**③ 맞는 설명은 다음 두 가지다.**

- **정지 구간의 관측 모호성:** 시연자가 멈춰 있으면 화면과 관절값이 그대로라, 시계가 없는 모델은 1초 지났는지 7초 지났는지 모른다. 같은 관측에 "더 기다려"와 "이제 움직여"가 동시에 달린다. 저장소 조사도 이것을 시연 정지 구간 문제로 정리했다(`research/R32_IL과_IK_결합구조_정책선택_실행모드.md` 5절, PACE 논문). 멈춤이 약 1.7초보다 길면 청크 전체가 "정지"인 학습 샘플이 생긴다. 13.4 s 유지가 짧아진 것의 이론적 의미가 이것이다. **[일반 이론 + 코드 구조로 해당 확인]**
- **정지 고착(되먹임):** 로봇에 올리면 "정지 청크 출력 → 로봇이 안 움직임 → 다음 관측이 같음 → 다시 정지"라는 고리가 생길 수 있다. 사용자가 들은 "자기회귀적 문제"의 실체는 아마 이것이다. 모델 구조가 아니라 **로봇·환경을 도는 폐루프(closed-loop) 되먹임**이다. 시연 때 이전 행동과 다음 행동이 비슷한 탓에 정책이 "지금 위치를 그대로 내는" 쪽으로 쏠리는 현상은 모방학습에서 copycat 문제로 불린다. 다만 SmolVLA는 이전 행동이 입력에 없고 관절 위치만 있어서 그 문제가 그대로 적용되지는 않는다. 우리 실물에서 측정한 적도 없다. **[일반 이론]**

부드러운 시연이 필요한 나머지 이유:
- 정책은 떨림·머뭇거림까지 따라 한다. 그래서 일부러 천천히 하지 않고 평소 속도로 움직이게 했다(시연 가이드 1장 2번).
- "CPU starvation" 경고가 뜬 판은 다시 찍었다. 프레임이 빠지면 빨리감기처럼 기록되기 때문이다(시연 가이드 3장).

주의: 정지가 전부 나쁜 것은 아니다. 가이드는 "일을 끝내면 멈춘다"를 가르치려고 끝에 2~3초 정지를 일부러 넣었다. 문제는 **과제 중간의 불필요한 긴 정지**다.

롤아웃의 "끊김"과 혼동하지 않는다: 50스텝마다 추론 시간만큼 팔이 멈추는 것(8번)은 실행 환경 문제로, 시연의 끊김과 별개다.

### 7-4. 발표에서 말할 문장

> "SmolVLA는 현재 관측 한 장만 보고 약 1.7초 치 동작을 예측합니다. 기억도 속도 정보도 없어서, 시연에서 같은 자세가 다른 뜻으로 반복되거나 오래 멈추면 구분하지 못합니다. 그래서 붓기를 한 번에, 멈춤 없이 하도록 시연을 다시 모았고, 유지 시간이 평균 13.4초에서 6.1초로 줄었습니다."

## 8. 21쪽: "일반 창 실행"이 뭐고 왜 추론 지연을 막나?

**결론: 예약 작업이 화면 없이 백그라운드로 띄우던 실행기를, 사용자가 로그인 화면에서 `start_scenario.bat`을 눌러 콘솔 창이 보이는 보통 프로그램으로 실행하는 것이다. 2.94 s가 약 0.5 s로 돌아온 원인 후보이지만, 단일 원인으로 확정되지 않았다. "일반 창 실행이 막았다"고 단정하면 과장이다.**

뜻:

| | 예약 작업 실행 | 일반 창 실행 |
|---|---|---|
| 기동 | Windows 작업 스케줄러(`AMRArmService` 등), 주행 PC SSH로 시작한 것으로 추정 | 담당자가 노트북에서 직접 실행 |
| 실행 파일 | `pythonw`(창 없는 Python) | `python.exe`(콘솔 창) |
| 프로세스 우선순위 | 7(보통보다 낮음) | 보통 |

왜 지연이 끊김이 되나: 추론이 제어 루프 안에서 동기로 돈다(`lerobot: rollout/inference/sync.py`). 50스텝마다 추론이 끝날 때까지 팔이 멈춘다. 그래서 작업 시간 ≈ 청크 수 × (구동 1.8 s + 추론 시간)이다. 추론이 3.3 s면 101 s 중 66.7 s가 대기였고, 100 s 안에 약 20청크밖에 못 돌아 시간 초과가 났다. 기준선은 추론 0.6 s 이하다.

왜 효과가 있어 보이나: Windows는 창이 없고 우선순위가 낮은 프로세스에 CPU 시간과 성능 코어를 덜 주는 경향이 있다. 추론은 GPU지만 영상 전처리와 카메라 스레드는 CPU다. 여기에 배터리 전력 제한이 겹쳤다는 해석이다. **이 동작 원리는 [일반 이론 + 가설]** 이고, 저장소도 "주요 가설", "확정 전"이라고 적었다.

측정 기록:

| 시점 | 전원 | 구성 | 추론 |
|---|---|---|---|
| 10-30 16:45 | 배터리 약 20% | 예약 작업, 전체 구성 | 2.94 / 3.38 s |
| 10-30 16:5x | 배터리 13% | 일반 창, **추론만** | 0.47~0.56 s |
| 10-30 18:0x | **충전** | 일반 창, 실행기 | 0.51 s |
| 10-30 20:09 | 배터리 약 41% | 기동 방식 미확인 | 3.30 s |
| 10-31 | 배터리 90~100% | 전체 구성 | 중앙값 0.58 s |
| 11-01 3회차 | 충전 분리 | 다른 GPU 작업(Isaac 렌더링) 동시 실행 | 평균 2.52 s |
| 11-01 4회차 | 충전 분리 | 렌더링 없음 | 평균 0.83 s |

읽는 법:
- 2.94 s와 0.5 s 측정은 전원이나 구성이 서로 달라 일반 창 효과만 분리되지 않는다.
- 저장소도 "전원만으로는 설명되지 않는다"고 적었고, 창 전경/비전경 판별 실험은 계획만 있다.
- 11-01처럼 같은 GPU를 쓰는 다른 작업도 큰 원인이다. 위 표의 정책 멈춤 평균은 워밍업 추론값과 다른 지표이므로 그대로 비교하지 않는다.
- **2.94 s도 노트북 로컬 추론 상태에서 나왔다.** 로컬 추론은 무선 지연을 없앤 조치이지 2.94 s를 고친 조치가 아니다.

운영 교훈: 일반 창으로 실행하고, 같은 GPU를 쓰는 작업을 끄며, 실행기 기동 시 `pour_infer_s` 0.6 s 이하를 확인한다.
