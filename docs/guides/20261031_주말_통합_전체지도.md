- 근거 표시: **[확인]** 로그·이벤트·코드로 확인, **[기록]** 팀 문서·PROGRESS 기록, **[가설]** 실험 전.

- 안전 규칙은 [CLAUDE.md](../../CLAUDE.md)를 따른다. 팔·차체 동작은 사용자 확인 후 실행한다.

## 4. 핵심 문제와 근거

### P1. 추론 약 3 s → 물따르기 시간 초과 (최우선)

- [확인] `run.log` 16:52 pour: 101.14 s 중 **0.3 Hz 루프 20회 = 66.7 s가 추론 대기**, 나머지 914회(중앙값 25 Hz) 36.7 s만 구동.
- [확인] 두 정책 모두 `n_action_steps=50`이라 50 step마다 제어 루프가 멈추고 추론한다(sync). 1청크 구동 약 1.8 s.
- 소요 시간 ≈ 청크 수 × (1.8 s + 추론 시간). 정상 66~94 s를 역산하면 약 29~41청크가 필요하다[가설].
  - 추론 3.3 s면 100 s 안에 약 20청크뿐이다. 로그의 20회와 일치한다.
  - 41청크 기준 100 s 안에 끝내려면 **추론 0.6 s 이하**여야 한다. 이 값을 S0 게이트로 둔다.
- 즉 `duration` 실패 2건은 정책 성능 문제로 보기 전에 실행 환경 문제로 설명된다. 시간 제한을 늘리는 것은 해법이 아니다.

| 시점 | 전원 | 구성 | 추론 |
|---|---|---|---|
| 10-30 오전 | 배터리 100% | 추론만 | 0.45~0.57 s |
| 16:45 | 배터리 약 20% | 예약 작업(pythonw, 우선순위 7), 전체 스택 | 2.94 / 3.38 s |
| 16:5x | 배터리 13% | 일반 창, 추론만 | 0.47~0.56 s |
| 18:0x | 충전 | 일반 창, 실행기 | 0.51 s |
| 20:09 | 배터리 약 41%(선형 추정) | 실행기 PID 20072(기동 방식 미확인) | 3.30 s, 0.3 Hz |

- 전원만으로는 설명되지 않는다. 가설은 셋이다[가설].
  - H1: 전경 창이 없는 프로세스가 배터리에서 낮은 성능 코어·클럭으로 배치된다.
  - H2: 배터리에서 카메라 3대·Astra 인코딩·추론 동시 부하가 전력 한도나 스레드 경합에 걸린다.
  - H3: 충전 분리 때 OMEN 성능 모드가 낮아진다. 재부팅 전 추론 2.1 s 사례와 규모가 같다.
- Windows 전원 오버레이는 현재 AC·DC 모두 최고 성능이다[확인]. H1을 약화하지만 배제하지는 않는다.
- 판별: 배터리 + 전체 스택에서 창 전경/비전경을 바꿔 `pour_infer_s`를 잰다. 팔은 움직이지 않는다.

## 5. 작업 순서

앞 단계 게이트를 통과해야 다음으로 간다. 수정이 생기면 3절에서 영향받는 단계를 함께 재검증한다.

**S0-1. 환경 정리 (팔·차 이동 없음)**
1. 주행 PC 접근 경로 확보, VNC 사용자 확인.
2. 작업 폴더를 이 폴더로 통일. 구 주문 서버 종료.
3. 실행기·주문 서버 출력의 파일 기록 추가.
4. Wi-Fi 6 GHz 복귀 후 IP `.157` 유지 확인.

**S0-2. 하드웨어 고정**
5. 손목캠 케이블 양 끝을 고정하고, 팔을 손으로 움직이며 끊김을 기록한다. 끊김 0회가 게이트다.

**S0-3. 배터리 전체 스택 측정 (게이트)**
6. 충전기를 뽑고 Astra 브리지 + 실행기로 `pour_infer_s`를 잰다. 전경/비전경 비교로 P1 원인을 가른다. **0.6 s 이하**가 게이트다.
7. 기동 절차를 시연용으로 고정한다.

**웹 단계 (2026-10-31 완료, 실물 미실행)**
- 손님 주문 → 관제 수락·거절 → START → 미션, STOP 잠금·해제, 관제 화면 흰 배경을 구현했다.
- 남은 연결 세 가지. 모두 차량·팔 검증이 필요해 실물 단계에서 한다.
