# 새 노트북 작업 인계 (조작·주문 서버·Astra 송신)

2026-10-30 작성. 지금까지 로봇에 실은 노트북(이하 기존 노트북)에서 하던 조작(IL) 쪽 작업을 새 노트북에서 이어 하기 위한 문서다.
새 노트북의 Claude Code가 이 문서를 위에서부터 따라 하면 된다. 🙋 표시는 사람이 직접 하거나 확인해 줘야 하는 단계다.

- 환경 설치(lerobot 패치, 파이썬 환경, 모델 받기, 장치 번호)는 [로봇 노트북 IL 추론 환경 구축](20261029_로봇노트북_IL_추론환경_구축.md)을 그대로 따른다. 이 문서는 그 뒤에 **달라진 점과 추가로 할 일**만 적는다.
- 시연 당일 운영은 [최종 시연 운영 절차](20261029_최종시연_운영절차.md), 주행 쪽과 주고받는 규칙은 [주행–조작 연동 구현 명세](20261029_주행_조작_연동_구현명세.md)를 따른다.

## 0. 꼭 지킬 규칙

- 팔이 움직이는 동작(토크 ON·이동·`stow`·`stow_right`·정책 실행)은 사용자 확인을 받고 실행한다. 모터·카메라를 읽기만 하는 진단은 예외다.
- HuggingFace의 데이터·모델은 받기만 한다. 지우거나 덮어쓰지 않는다.
- 커밋은 파일 단위로 스테이징한다(`git add .`, `-A` 금지). 커밋·푸시 전에 사용자에게 묻는다.
- 비밀번호·토큰·SSH 키는 저장소나 문서에 적지 않는다.

## 1. 지금 상태 (2026-10-30 기준)

**전체 구성**

| 기기 | 하는 일 | 연결 |
|---|---|---|
| 노트북(로봇 탑재, 이 문서의 대상) | 조작 실행기(SmolVLA 80 물따르기·컵배치), 주문 서버(손님 웹·관제), Astra 영상 → Pi 송신 | 팔 2개·손목캠 2대·Astra를 USB로 연결 |
| 주행 PC(팀원) | 미션 진행 `tools/jdamr/water_service.py`, Pi에 ssh로 주행 명령 | Wi-Fi |
| Pi(로봇) | 주행·정밀주차, Astra 영상 수신기(`jdamr-astra-tcp.service`, 포트 5600) | Wi-Fi |

**한 회차의 흐름**
1. 주문(손님 QR 또는 주행 PC의 start)이 들어오면 노트북이 양팔을 이동 자세(`place_end`)로 접는다.
2. 주문 서버 `/api/state`의 `drive`가 `{"next":"kitchen","arms_ready":true}`가 되면 주행 PC가 출발한다.
3. 급수대 정차·정렬 → 주행 PC가 `POST /api/align/confirm {"station":"kitchen"}` → 물따르기 → 오른팔만 접음(왼팔은 컵을 쥔 채).
4. `next=table`, `arms_ready=true` → 테이블 1로 이동 → `align/confirm table` → 컵배치 → 양팔 `place_end`.
5. `next=dock`, 주문 SUCCEEDED, 팔 `stowed` → 도크 복귀.

**2026-10-30 통합 시험 결과(1회, 차 실제 주행, 병·컵 실물)**

| 단계 | 결과 |
|---|---|
| 주문 → 양팔 접기 | ✅ 6.3 s |
| 출발 → 급수대 정렬 완료 | ✅ 약 7분 |
| 물따르기 | ✅ 시작 자세 6.2 s + 정책 94.2 s, 자동 끝 감지 |
| 오른팔 접기 | ❌ 오른쪽 손목캠 USB가 빠져 관측 실패 → `stow_right`로 수동 복구 ✅ |
| 테이블 도착 | ✅ |
| 컵배치 | ❌ 정렬 신호를 받은 순간 손목캠 재연결 중이라 팔을 움직이지 않고 즉시 실패 |

이 실패들을 막으려고 같은 날 아래를 고쳤다(5절의 PR). **수정본으로는 아직 실차 회차를 돌리지 않았다.**
- 팔 접기·자세 확인은 카메라 없이 모터 위치만 읽는다.
- 카메라가 끊기면 마지막 프레임으로 계속 돌고 뒤에서 다시 연결한다(`tools/rollout/camera_fallback.py`). 다시 연결하는 동안에도 로봇은 연결된 것으로 본다.
- 오른팔만 접는 복구 명령 `rollout_service.py stow_right`를 추가했다.

## 2. 새 노트북 준비 순서

### 2-1. 🙋 저장소 받기와 기본 설치
1. 환경 구축 가이드 0~7절을 그대로 한다(저장소 clone, lerobot 패치, `so101_env`, 모델 받기, 토크나이저 경로 수정).
   ```powershell
   git clone -c core.autocrlf=false https://github.com/mmporong/bimanual-robot.git
   ```
2. 사용자 이름이 `USER`가 아니면 가이드 5-4절의 하드코딩 경로를 고친다. `tools/rollout/start_scenario.bat`의 `PY`, `POUR`, `PLACE`도 여기에 포함된다.

### 2-2. Astra SDK 위치
- Astra SDK(`AstraSDK-v2.1.3-…-vs2015-win64`)와 드라이버(`astra-win32-driver-4.3.0.22`)는 저장소에 없다. 🙋 기존 노트북에서 복사해 온다.
- 브리지는 SDK의 `bin` 폴더를 다음 순서로 찾는다(`tools/camera/astra_sdk.py`).
  1. 환경 변수 `ASTRA_SDK_BIN`
  2. `%USERPROFILE%\Downloads`, `D:\astra`, `C:\astra`, `%USERPROFILE%\astra` 아래의 `AstraSDK-…\[AstraSDK-…\]bin`
- 다른 곳에 풀었다면 지정한다(새 터미널부터 적용).
  ```powershell
  setx ASTRA_SDK_BIN "D:\somewhere\AstraSDK-v2.1.3-94bca0f52e-20210608T034051Z-vs2015-win64\bin"
  ```
- 드라이버를 설치한 뒤 장치 관리자에 `ORBBEC Depth Sensor`가 정상으로 떠야 한다. OBS Studio도 설치해야 한다(가상 카메라 드라이버용).

### 2-3. 장치 번호 (노트북이 바뀌면 반드시 다시 함)
- 팔 COM 포트: 가이드 6-1절. 새 번호를 `start_scenario.bat`의 `LEFT_PORT`, `RIGHT_PORT`에 넣는다(기존 노트북은 왼팔 `COM15`, 오른팔 `COM16`).
- 손목캠 왼쪽·오른쪽: 가이드 6-3절. `tools/camera/resolve_camera_indices.py`의 `LEFT_DEVPATH_HINT`, `RIGHT_DEVPATH_HINT`를 새로 뽑는다.
  - 기존 노트북 마지막 값은 왼쪽 `2bd3af6b`(Innomaker-U20CAM-720P), 오른쪽 `1b3f2dc8`(USB 2.0 PC Cam)이었다. 새 노트북에서는 경로가 바뀐다.
  - 왼쪽 손목 화면에는 순정 SO-101 집게가, 오른쪽에는 오른손 집게가 보인다.
- Astra 보정값 `config/camera/astra_params.json`은 **같은 Astra 장치면 그대로 쓴다**(장치에 저장된 공장값). Astra를 바꿨다면 브리지를 끈 상태에서 `tools\camera\astra_camera_params.py`를 다시 실행한다.
- 캘리브레이션(`calibration/bi_follower/*.json`)과 자세 파일(`config/rollout_poses/*.json`)은 팔에 묶인 값이라 그대로 쓴다. 다시 캘리브레이션하지 않는다.

### 2-4. 🙋 네트워크
1. Wi-Fi는 **`aicampus_286_6G`**(6 GHz)에 연결하고 1순위 자동 연결로 둔다. 2.4 GHz는 강의실에서 혼잡해 Astra 송신이 2 fps로 떨어졌다.
   ```powershell
   netsh wlan set profileorder name=aicampus_286_6G interface=Wi-Fi priority=1
   netsh wlan set profileparameter name=robot connectionmode=manual   # robot 프로필이 있으면
   ```
2. 새 노트북 IP를 확인한다(`ipconfig`의 Wi-Fi IPv4). 기존 노트북은 `192.168.0.175`였다. **IP가 다르면**:
   - 주행 담당에게 알린다. 주행 PC의 `water_service_api.py serve --order-url http://<새 IP>:8765`를 바꿔야 한다.
   - 손님 QR을 다시 만든다(아래 2-6).
3. 방화벽에서 주문 서버 포트를 연다(관리자 PowerShell). 휴대폰 주문·관제와 주행 PC 접속에 필요하다.
   ```powershell
   New-NetFirewallRule -DisplayName "order-server 8765" -Direction Inbound -Protocol TCP -LocalPort 8765 -Action Allow -Profile Any
   ```
   - 조작 실행기(8770)는 노트북 안에서만 쓰니(`127.0.0.1`) 열지 않는다.
4. Pi(`192.168.0.159`)의 5600 포트에 닿는지 확인한다: `Test-NetConnection 192.168.0.159 -Port 5600`(ping은 막혀 있을 수 있다).

### 2-5. 🙋 전원
- 노트북은 차에 실려 배터리로 돈다. 전원 모드를 최고 성능으로 둔다. 기존 노트북(ASUS)은 Silent에서 추론 1회 0.99 s, Performance에서 0.5~0.6 s, 충전 중 0.4 s였다.
- 시험 중에는 절전·화면 꺼짐을 끈다(Remote Control·브리지가 끊긴다).

### 2-6. 손님 주문 QR
- 주소는 `http://<노트북 IP>:8765/order?table=1`이다(주행에는 테이블 1만 등록돼 있다). 관제는 `/control`.
- QR 만들기 예:
  ```powershell
  & $PY -m pip install segno
  & $PY -c "import segno; segno.make('http://<노트북 IP>:8765/order?table=1', error='m').save('table1_qr.png', scale=12)"
  ```

### 2-7. 준비 점검 (한 번에)
팔 배터리 ON, USB 연결, 실행기는 끈 상태에서 저장소 루트에서 실행한다. 읽기만 한다.
```powershell
& $PY tools\rollout\setup_check.py
```
- 저장소·파이썬·CUDA·lerobot 패치·패키지·모델·토크나이저 경로·팔 모터(응답·전압)·Astra SDK와 장치·손목캠 경로 힌트·Wi-Fi·IP·방화벽·Pi 5600·전원 구성을 점검하고, 끝에 `실패 N, 주의 N`을 요약한다.
- 실패 항목에는 고칠 곳이 함께 나온다. 출력 전체를 사용자나 Claude Code에 공유한다.

## 3. 실행 순서 (매번)

1. 🙋 팔 배터리 2개 ON, USB 연결(팔 2, 손목캠 2, Astra). 실행기를 켜기 전에 모터 응답과 **배터리 전압**을 읽기 전용으로 점검한다(팔은 움직이지 않음).
   ```powershell
   & $PY tools\rollout\arm_health.py --left COM15 --right COM16   # 새 노트북 COM 번호로
   ```
   - 12개 모터가 모두 응답하고 `정상`이 나와야 한다. `⚠ 전압 낮음`(9 V 미만)이면 충전된 배터리로 바꾼다. 2026-10-30에는 왼팔이 9.2 → 8.4 V로 1시간 반 만에 떨어졌다.
2. Astra 브리지(창 하나, 계속 켜 둠). IL 상단 카메라(가상 카메라)와 Pi 송신을 함께 한다.
   ```powershell
   cd <REPO>
   & $PY tools\camera\astra_rgb_virtualcam_bridge.py --send-pi 192.168.0.159:5600
   ```
   - 10초마다 `[ast1 HH:MM:SS] 연결=True 보냄=… 최대공백 송신=…s 카메라=…s`가 나온다. 송신 약 10 fps, 최대 공백 0.11 s 근처면 정상이다.
   - `송신 공백`이 계속 0.3 s를 넘으면 Wi-Fi 문제다(카메라 공백은 정상인데 송신만 막힘). 6 GHz에 붙어 있는지 확인한다.
3. 카메라 번호 확인: `& $PY tools\camera\resolve_camera_indices.py` → `left`, `right`, `depth` 세 값.
4. 실행기와 주문 서버: `.\tools\rollout\start_scenario.bat`. 관제 `http://127.0.0.1:8765/control`의 Manipulation이 `ready`가 될 때까지 기다린다(약 90~110 s).
   - `manip-service` 창이 바로 닫히면 오류가 안 보인다. 같은 명령을 PowerShell에 직접 붙여 실행해 로그를 본다. 흔한 원인은 팔 전원 꺼짐(`Missing motor IDs`)이다.
5. 주행 담당에게 "ready, start 가능"을 알린다. 출발은 주행 PC의 `water_service_api.py start`로 한다. 노트북에서 누를 버튼은 없고, 관제의 [정렬 완료]도 누르지 않는다(주행 PC가 보낸다).

## 4. 문제가 생겼을 때

[최종 시연 운영 절차](20261029_최종시연_운영절차.md) 6절 표를 따른다. 2026-10-30에 실제로 겪은 것:

| 증상(로그) | 원인 | 조치 |
|---|---|---|
| 실행기가 바로 꺼짐, `Missing motor IDs` | 팔 서보 전원 꺼짐 | 배터리 ON 후 재시작 |
| 대기 중 `no status packet` 반복 | 한쪽 팔 배터리 빠짐 | 팔을 받치고 배터리를 꽂은 뒤 실행기 재시작 |
| `ClearCommError … 액세스가 거부` / `Port is in use` | USB가 빠졌다 다시 붙음(팔 포트) | 실행기 재시작. 진행 중 주문이면 이어서 `stow_right` |
| `[camera …] 프레임 끊김`이 자주 | 손목캠 USB 접촉·대역폭 | 보호 기능이 버티지만 근본 대책은 USB 고정·포트 변경 |
| 브리지 종료, `Failed to send a USB control request` | Astra USB 순간 끊김 | Astra를 뽑았다 꽂고 브리지 재시작 → 실행기도 재시작(가상 카메라가 끊김) |
| 물따르기 후 테이블 출발 안 함(`arms_ready=false`, 팔 `hold`) | 오른팔 자동 접기 실패 | 병을 놓았는지 확인하고 `rollout_service.py stow_right` |
| 주행 PC의 정렬 신호가 409 `not_waiting` | 주문이 이미 실패·종료됨 | 정상 거절. `/api/state`의 주문 상태를 확인하고 새 회차로 |

진행 중인 주문은 실행기를 재시작해도 주문 서버에 남는다(ALIGN 단계는 최대 1시간 대기). 주행 PC의 미션은 물따르기 뒤 테이블 출발 신호를 최대 300 s만 기다리므로, 그보다 오래 걸린 복구 뒤에는 주행 담당이 남은 구간을 수동으로 이어야 한다.
