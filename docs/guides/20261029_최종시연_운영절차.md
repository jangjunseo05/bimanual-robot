# 최종 시연 운영 절차 (주문 웹 → 물따르기 → 컵배치 → 도크 복귀)

> 실행 절차는 [로봇 구동 런북](20261031_로봇구동_런북.md)을 따른다. 아래의 포트·IP·경로·성능 모드는 구 노트북 값이 섞여 있고, 주행 PC가 웹을 따라가므로 정렬 완료 버튼을 누를 일도 없다.

2026-10-29 작성. 웹에서 주문하면 상주형 조작 실행기가 미리 올려 둔 SmolVLA 80 두 정책으로 팔을 움직이는 시연 절차다.
실행 근거 코드는 다음과 같다.
- 조작 실행기: `tools/rollout/rollout_service.py`
- 주문 서버: `apps/service_order/service_order_server.py`
- 미션 연결: `src/mission/service_execution_backend.py`의 `RolloutServiceBackend`
- 한 번에 켜기: `tools/rollout/start_scenario.bat`

## 0. 지금 되는 것과 안 되는 것 (2026-10-30 갱신)

| 항목 | 상태 |
|---|---|
| 시작할 때 두 정책 미리 로드·예열, 호출 즉시 추론 | 실차 확인(준비 약 90~110 s) |
| 웹 주문 → 수락 → START → 미션 시작 | 구현됨(2026-10-31). 손님 `/order`, 관제 `/control`. 주문만으로는 팔이 움직이지 않는다 |
| 이동 중 팔 이동 자세(`place_end`) 유지 | 실차 확인: 주문 직후 양팔 접기 6.2~6.3 s |
| 주방·테이블 정렬 후 바로 물따르기·컵배치 | 실차 확인: 급수대 정렬 → 물따르기 성공(정책 94 s, 자동 끝 감지) |
| **주행 자동 연동** | 주행 PC `tools/jdamr/water_service.py`(PR #86 브랜치)가 `/api/state`의 `drive`를 보고 출발하고 `/api/align/confirm`을 보낸다. 2026-10-30 통합 1회: 급수대·물따르기·테이블 도착까지 이어졌고, 오른쪽 손목캠 USB 끊김으로 컵배치는 못 함 |
| 카메라 끊김 보호 | 2026-10-30 추가(`tools/rollout/camera_fallback.py`). 끊기면 마지막 프레임으로 계속하고 뒤에서 다시 연결한다. 팔 접기는 카메라 없이 모터 위치만 읽는다 |

알려 주신 단건 명령과 같은 설정이다.

| 작업 | 정책 | 시작 자세 | 끝 자세 | 자동 종료 | 최대 시간 |
|---|---|---|---|---|---|
| 물따르기 | `water_pour_chassis_smolvla_80` step 16000 | `pour` | `final` | `pour` | 100 s |
| 컵배치 | `cup_place_chassis_smolvla_80` step 7000 | 없음 | `place_end` | `place` | 50 s |

두 작업 모두 `max_relative_target=15`, 끝 자세 판정 허용치는 기본 10°다.

## 1. 팔 자세 흐름 (요구사항: 이동 중에는 컵배치 끝 자세 유지)

| 시점 | 차 | 왼팔 | 오른팔 | 누가 움직이나 |
|---|---|---|---|---|
| 주문 접수 직후 | 도크에 정지 | `place_end` | `place_end` | 미션이 실행기에 `/stow` 호출 |
| 도크 → 주방 이동 | 이동 | `place_end` | `place_end` | (유지) |
| 주방 정렬 완료 | 정지 | `pour` 시작 자세 → 정책 | 정책 | `/run/pour` |
| 물따르기 끝(작업 끝 감지) | 정지 | **컵을 쥔 상판 적재 자세 유지** | `place_end`로 접음 | 실행기가 자동으로 |
| 주방 → 테이블 이동 | 이동 | 컵 유지 | `place_end` | (유지) |
| 테이블 정렬 완료 | 정지 | 정책 | 정책 | `/run/place` |
| 컵배치 끝 | 정지 | `place_end` | `place_end` | 실행기 끝 자세 |
| 테이블 → 도크 이동 | 이동 | `place_end` | `place_end` | (유지) |

- 주방 → 테이블 구간에서는 **왼팔을 `place_end`로 바꾸지 않는다.**
  - 이 자세가 컵배치 정책의 시작 자세(컵을 쥐고 차체에 실은 자세)라서, 바꾸면 컵을 떨어뜨리고 컵배치가 시작될 수 없다.
  - 그래서 이 구간은 오른팔만 접는다.
- 그리퍼는 이동 자세가 건드리지 않는다. 쥐고 있는 컵은 그대로 쥐고 있다.
- 물따르기가 작업 끝 감지 없이 최대 시간(100 s)으로 끝나면 오른팔을 접지 않는다. 병을 아직 쥐고 있을 수 있어서다. 이때 미션은 `POUR_END_NOT_DETECTED`로 실패하고, 사람이 확인한다.
- 실패·중단으로 팔이 그 자리에 멈추면 관제 화면의 팔 상태가 "그 자리 유지(확인 필요)"가 된다. 이 상태에서는 차를 움직이지 않는다.

## 2. 사전 준비 (시연 30분 전)

1. 팔 전원 ON, USB 연결
   - 왼팔 `COM15`, 오른팔 `COM16`, 손목 카메라 2대, Astra
2. 노트북 전원: 차에 싣고 다니므로 배터리로 돈다. 시연 전에 충전해 두고, ASUS 모드를 **Performance**(Armoury Crate 또는 Fn+F5)로 둔다.
   - Silent 모드에서는 추론 1회가 0.99 s, Performance에서는 0.52~0.59 s였다(2026-10-29 배터리 실측). Turbo는 충전기 연결 때만 된다.
3. Wi-Fi: 노트북은 **`aicampus_286_6G`**(6 GHz). 같은 공유기의 `aicampus_286`(2.4 GHz)·`_5G`와 같은 망(`192.168.0.x`)이다. 노트북 IP `192.168.0.175`, Pi `192.168.0.159`, 주행 PC `192.168.0.217`.
   - 2.4 GHz에서는 강의실 혼잡으로 노트북→공유기 왕복이 최대 2.4 s, Astra 송신이 2 fps까지 떨어졌다. 6 GHz로 옮기자 10 fps, 최대 공백 0.11 s, Pi까지 평균 54 ms였다(2026-10-30).
   - `aicampus_286_6G`를 1순위 자동 연결로 두고(`netsh wlan set profileorder name=aicampus_286_6G interface=Wi-Fi priority=1`), `robot`은 자동 연결을 껐다(`connectionmode=manual`). 켜 두면 노트북이 `robot`으로 넘어가 주행 PC·Pi와 끊긴다.
   - IP가 바뀌면 주문 QR을 다시 만들고 주행 담당에게 알린다.
4. 컵·물병·자갈을 급수대의 테이프 위치에 둔다.
   - 컵배치를 할 테이블 위는 비워 둔다.
5. Astra 브리지를 띄운다(창 하나, 시연 내내 유지). 같은 프로그램이 IL용 가상 카메라와 Pi 정밀주차용 RGB·정렬 깊이 송신(AST1)을 함께 한다.
   ```
   cd C:\Users\USER\Desktop\프로젝트\최종프로젝트\bimanual-robot-git
   & "C:\Users\USER\miniconda3\envs\so101_env\python.exe" tools\camera\astra_rgb_virtualcam_bridge.py --send-pi 192.168.0.159:5600
   ```
   - 10초마다 `[ast1] 연결=True 보냄=…`이 늘어나면 정상이다(10 fps, 약 1.35 MB/s).
   - `Failed to send a USB control request`가 나오면 Astra USB를 뽑았다 다시 꽂는다.
   - 보정값 파일 `config/camera/astra_params.json`이 없다고 나오면, 브리지를 끈 상태에서 `tools\camera\astra_camera_params.py`를 한 번 실행한다.
   - 장치는 한 프로그램만 열 수 있다. 브리지를 두 개 띄우지 않는다.
6. 카메라 번호 확인: `python tools\camera\resolve_camera_indices.py`에서 `left`, `right`, `depth`가 모두 나와야 한다.
7. 다른 롤아웃·텔레옵 창을 모두 닫는다. 팔 포트는 한 프로그램만 열 수 있다.

## 3. 켜기 (차가 도크에 있을 때)

```
tools\rollout\start_scenario.bat
```
- 창 `manip-service`(조작 실행기)와 `order-server`(주문 서버)가 뜨고, 관제 화면 `http://127.0.0.1:8765/control`이 열린다.
- 조작 실행기가 정책 두 개 로드 → 팔·카메라 연결 → 예열을 마치면 `준비 완료 …s -> 호출 대기`를 출력한다. 실차 연결 실측은 약 100 s(Performance, 배터리)·157 s(Silent)였다(2026-10-29).
  - 관제 화면 `조작 실행기` 칸이 `준비됨`이 될 때까지 주문하지 않는다.
  - 준비 중에 들어온 주문은 준비가 끝날 때까지 기다린다.
- 이때까지 팔은 움직이지 않는다. 그리퍼가 물체를 밀고 있으면 미는 힘만 줄인다.

## 4. 주문과 진행

**주문**
- 손님 휴대폰(같은 Wi-Fi): `http://<노트북 IP>:8765/order?table=1`
  - 노트북 IP는 `ipconfig`의 Wi-Fi IPv4다. 2026-10-29 기준 `192.168.0.15`였다.
- 또는 관제 화면의 직원 대리 주문
- 주행 쪽에 등록된 테이블은 `table_01` 하나다. 주문도 **테이블 1**로 받는다.

**수락과 시작**
- 손님 주문은 관제 화면 [주문 목록]에 `수락 대기`로 들어온다. [수락] 또는 [거절]을 누른다.
- 수락하면 상단 **START**가 켜진다. 차가 도크에 있고 주변이 비었는지 확인한 뒤 누른다.
- 직원 대리 주문은 수락된 상태로 들어가므로 START만 누른다.
- **STOP**은 언제든 누를 수 있고 확인 창 없이 바로 나간다. [긴급 정지 해제] 전에는 다음 단계와 START가 막힌다.

**진행** (관제 화면 위쪽 파란 배너를 따라간다)
1. START를 누르면 차는 도크에 서 있는 상태에서 **양팔이 `place_end`로 접힌다**(약 5 s).
2. 배너에 "차를 주방(급수대)로 이동·정렬하세요"가 뜨면 주행 담당이 출발한다.
3. 급수대 정차·정렬이 끝나면 **[정렬 완료 → pour 정책 실행]**을 누른다. 물따르기가 바로 시작된다.
4. 물따르기가 끝나면 오른팔이 접히고, 배너가 "차를 테이블로 이동·정렬하세요"로 바뀐다. 주행 담당이 출발한다.
5. 테이블 정차·정렬이 끝나면 **[정렬 완료 → place 정책 실행]**을 누른다.
6. 컵배치가 끝나 양팔이 `place_end`가 되면 주문이 성공으로 끝난다. 주행 담당이 도크로 복귀한다.

⚠️ **팔이 움직이는 동안(`조작 실행기` 칸이 `실행 중`) 차를 움직이지 않는다.** 정렬 완료 버튼은 차가 완전히 멈춘 뒤에만 누른다.
- 배너에 "⚠ 팔이 이동 자세가 아닙니다"가 보이면 출발하지 않는다.

## 5. 주행 연동 계약 (주행 담당용)

> 구현 명세(파일·줄 번호·브리지 상태 기계·검증 절차)는 [주행–조작 연동 구현 명세](20261029_주행_조작_연동_구현명세.md)를 따른다. 아래는 요약이다.

주행 자동화를 붙일 때는 아래 두 가지만 쓰면 된다. 둘 다 주문 서버(노트북) API다.

| 용도 | 호출 | 내용 |
|---|---|---|
| 다음 목적지·출발 가능 여부 | `GET http://<노트북 IP>:8765/api/state` → `execution_backend.drive` | `{"next": "kitchen"\|"table"\|"dock"\|null, "arms_ready": bool}`. `arms_ready`가 `true`이고 `running_policy`가 `null`일 때만 출발한다 |
| 정차·정렬 완료 | `POST http://<노트북 IP>:8765/api/align/confirm` `{"station": "kitchen"\|"table"}` | 관제 버튼과 같다. 받는 즉시 해당 정책을 실행한다 |

**지금 주행 코드의 한계** (PR #86 기준 `jdamr_depart.py go table_01`)
- 도크 → 급수대 → 테이블1 → 도크를 한 번에 달린다.
- 각 정차 지점에서는 `--dwell-s`(최대 120 s) 동안만 머물고 출발한다. 조작이 끝났는지 기다리지 않는다.
- 물따르기는 시작 자세 이동 5 s + 정책 최대 100 s + 오른팔 접기 5 s라서 **120 s를 넘을 수 있다.** 그러면 팔이 움직이는 중에 차가 출발한다.

따라서 연속 주행 그대로는 쓰지 않는다. 시연 전에 주행 쪽에 다음 둘 중 하나가 필요하다.
1. **권장**: 정차 대기를 시간 대신 위 계약으로 바꾼다. `drive.next`가 다음 지점으로 바뀌고 `arms_ready`가 `true`가 될 때까지 기다린다.
2. 구간별로 나눠 실행한다. 급수대까지 → (조작) → 테이블까지 → (조작) → 도크. 각 구간 출발은 사람이 위 배너를 보고 한다.

## 6. 중단·비상

| 상황 | 조치 |
|---|---|
| 팔이 이상하게 움직임 | 관제 **STOP**을 누른다. 실행기에 `/stop`을 보내고, 팔은 그 자리에서 유지한다 |
| 팔이 위험하게 힘을 받고 있음 | 실행기 창에서 Ctrl+C로 끈 뒤 `python tools\rollout\emergency_torque_off.py`로 토크만 끈다(팔을 움직이지 않음). **팔이 떨어질 수 있으니 손으로 받친다** |
| 정렬을 잘못 눌렀음 | 정책이 시작됐으면 **STOP** |
| 물따르기 끝 감지 실패(`POUR_END_NOT_DETECTED`) | 오른팔이 병을 쥐고 있는지 확인한다. 사람이 병을 회수하고, 다음 주문 전에 `python tools\rollout\rollout_service.py stow`로 팔을 접는다(차 정지 상태에서) |
| 물따르기는 됐는데 오른팔 접기 실패(`right_stow` 오류, 팔 `hold`, 테이블 출발 막힘) | 오른손이 병을 놓았는지 확인하고, 차가 선 상태에서 `rollout_service.py stow_right`. 오른팔만 접고 왼팔(컵)은 그대로 두며, 성공하면 `carrying_cup`·`arms_ready=true`로 출발이 풀린다. 주문은 ALIGN_TABLE 그대로 유지된다 |
| 실행기를 재시작해야 함(USB가 빠졌다 붙음 등) 주문 진행 중 | 재시작하면 팔 상태가 `unknown`이 되어 출발이 막힌다. 물따르기 뒤라면 재시작 후 `stow_right`로 `carrying_cup`을 다시 만든다(이미 접혀 있으면 1° 안이라 움직이지 않음) |
| 팔 하나가 응답 없음(`no status packet`, 배터리 빠짐) | 그 팔의 모든 작업이 팔을 움직이지 않고 실패한다. 빠진 팔은 힘이 풀리니 받친다. 배터리를 다시 꽂고 실행기를 재시작한다 |
| `start_scenario.bat`의 `manip-service` 창이 바로 닫힘 | 창이 닫혀 오류가 안 보인다. 같은 명령을 PowerShell에서 직접 실행해 로그를 본다. 2026-10-30 원인은 팔 서보 전원 꺼짐(`Missing motor IDs`)이었다 |


## 7. 끝내기
1. 팔을 받칠 준비를 한 뒤 `rollout_service.py shutdown`으로 끈다.
   - 토크는 `disable_torque_on_disconnect=false`라 켜진 채 남는다.
   - 힘을 빼려면 `emergency_torque_off.py`를 쓴다.
2. `order-server` 창을 닫고, Astra 브리지 창을 닫는다.

## 8. 첫 리허설에서 꼭 볼 것 (실물 미검증 항목)
1. 준비 완료 시간(`timings.ready_total_s`)과 GPU 메모리(약 2.3~2.6 GB 예상)
2. 주문 직후 양팔 접기(`/stow`)가 부드럽게 끝나는지
   - 시작 자세가 `place_end`와 크게 다르면 최대 20°/s로 천천히 움직인다.
3. 물따르기 끝 → 오른팔 접기가 컵을 쥔 왼팔과 부딪히지 않는지
4. 대기가 수 분일 때 첫 호출에서 카메라 시간 초과가 없는지
5. 물따르기 실제 소요 시간
   - 주행 쪽 정차 대기 설계에 필요하다. `/status`의 `last_result.run_s`를 본다.
6. 컵배치 끝 자세(`place_end`) 도달과 관제 화면 팔 상태 "이동 자세"
